# Публикация КИЗов возвратов

Три сценария `/api/returns/incoming_returns`, `/api/returns/receive_unidentified`
и `/api/returns/receive_missing_sticker` сохраняют событие в
`public.kiz_returns_outbox` в той же транзакции, что приход и марки.
Ошибка записи outbox откатывает приёмку. Старые записи марок автоматически
не отправляются.

Один успешный запрос создаёт одно событие со всеми его КИЗами:

```json
{"mark_codes": ["код1", "код2"]}
```

Пустые строки, строки из пробелов и `broken` (без учёта регистра и внешних
пробелов) исключаются. Дубли внутри сообщения удаляются, порядок сохраняется.
Остальные коды передаются без изменения, включая разделители и пробелы.
Если подходящих кодов нет, задание не создаётся. Запись самих марок в
`goods_returns_mark_list` и уведомление 1С продолжают работать как раньше.

## Развёртывание

1. До запуска новой версии применить `migrations/kiz_returns_outbox.sql`
   в БД приложения. Миграция создаёт только новую таблицу и её индекс.
   Роли приложения нужны SELECT/INSERT/UPDATE на таблицу и доступ к sequence,
   если миграция выполняется другой ролью.
2. Указать `RABBITMQ_URL` в окружении приложения для отдельного брокера КИЗов.
   Локально проверен брокер `141.133.184.144:5672`, vhost `/`.
   Секрет подключения не хранится в отслеживаемых файлах.
3. При необходимости изменить параметры:

   | Переменная | Значение по умолчанию |
   |---|---|
   | `KIZ_RETURNS_EXCHANGE` | `wms.events` |
   | `KIZ_RETURNS_ROUTING_KEY` | `wms.kiz_returns` |
   | `KIZ_RETURNS_POLL_INTERVAL` | 1 секунда |
   | `KIZ_RETURNS_PUBLISH_TIMEOUT` | 10 секунд |

4. Запустить/перезапустить приложение. Обработчик запускается независимо от
   `CONSUMERS_START`; существующее подключение стикеров `RABBIT_*` не меняется.

При отсутствии `RABBITMQ_URL` приёмка продолжает записывать задания, но
обработчик не запускается; приложение пишет предупреждение в лог.

## Доставка и сбои

Известная привязка: `wms.events` (topic, durable) → `wms.kiz_returns` →
`fbs2.kiz_returns` (durable). Обработчик не создаёт и не изменяет топологию.
Используются persistent messages, publisher confirms и mandatory publish:
отсутствие маршрута или подтверждения считается ошибкой отправки.

Задания выбираются с `FOR UPDATE SKIP LOCKED`: несколько процессов API могут
работать одновременно. Блокировка удерживается до завершения отправки и
обновления статуса. Весь сетевой этап ограничен publish timeout.
При ошибке увеличивается `attempts`, сохраняется тип ошибки в `last_error`,
следующая попытка назначается через 2, 4, 8, … секунд, максимум через 300
секунд. Число попыток не ограничено. После восстановления RabbitMQ очередь
заданий продолжит обрабатываться. После перезапуска приложения задания также
сохраняются. Для работы нужны доступная БД и запущенное приложение.

`sent_at` заполняется только после подтверждения RabbitMQ. Это подтверждение
приёма сообщения брокером, а не успешной обработки потребителем. При сбое
после публикации, но до фиксации `sent_at`, возможна повторная доставка.
AMQP `message_id=kiz-returns-<outbox id>` стабилен при повторной отправке;
потребитель должен поддерживать идемпотентность. Тело сообщения содержит
только `mark_codes`.

Проверка накопившихся заданий:

```sql
SELECT id, created_at, attempts, next_attempt_at, last_error
FROM public.kiz_returns_outbox
WHERE sent_at IS NULL
ORDER BY created_at;
```

Отправленные записи сохраняются; автоматическое удаление не включено.

## Проверка

Обычные тесты: `PYTHONPATH=. .venv/bin/pytest -q`.
Для интеграционных проверок указать `TEST_KIZ_POSTGRES_URL` (роль с CREATEDB)
и `TEST_KIZ_RABBITMQ_URL`, направленные на изолированные тестовые сервисы,
и запустить `tests/test_kiz_returns_integration.py`. Проверка PostgreSQL
создаёт и удаляет собственную временную БД. Проверка RabbitMQ создаёт
отдельный обменник со случайным именем и временную очередь.
